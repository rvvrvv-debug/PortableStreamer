# PROJECT_SPEC.md — PortableStreamer v2.02

Плановый стример (playout server) на C# WinForms + GStreamer + MediaMTX.

> **Статус документа.** Это третья редакция спецификации. Две предыдущие описывали
> архитектуру, которая в процессе разработки была заменена на более простую и надёжную
> (см. раздел «История решений»). Всё, что описано ниже, **проверено живыми прогонами**,
> включая непрерывный эфир 18 минут без рассинхронизации.

---

## 1. Назначение

Программа в назначенное время автоматически запускает трансляцию плейлиста:

```
заставка (картинка) → основное видео → финальная заставка
```

и отдаёт её на внешний CDN (YouTube, Twitch, CDNvideo и любой RTMP-сервер).

Пользователь запускает программу заранее, задаёт время старта, собирает задание
и может «забыть» о ней — эфир начнётся сам.

---

## 2. Стек и ограничения

| Параметр | Значение |
|---|---|
| Язык | C# (.NET 10) |
| UI | Windows Forms, весь `InitializeComponent` написан вручную |
| Компиляция | Native AOT, `TopLevelStatements=disable` |
| Медиа | GStreamer (портативная сборка в `tools/gstreamer`) |
| Ретрансляция | MediaMTX (`tools/mediamtx.exe`) |

Жёсткие ограничения:

- **никакой рефлексии** (несовместима с AOT);
- **никакого Newtonsoft.Json** — при необходимости только `System.Text.Json` с генераторами;
- **никакого `Microsoft.VisualBasic.Interaction.InputBox`** (использует ResourceManager, падает в AOT) — применяется собственная форма `ShowInputDialog`;
- все внешние бинарники портативные, лежат рядом с `.exe`;
- кириллица и `!` в путях поддерживаются: пути к файлам передаются GStreamer с заменой `\` на `/`.

## 4. Ключевая архитектура

### 4.1. Плейлист — список сегментов, а не файлов

```csharp
enum SegmentKind { Image, File }
record PlaylistSegment(SegmentKind Kind, string Path, int DurationSeconds, bool HasAudio = true);
```

- **Image** — картинка, которая генерируется прямо в эфирном потоке
  (`imagefreeze num-buffers = секунды × fps`). Никаких промежуточных MP4.
- **File** — видео пользователя; `HasAudio` определяется анализом файла.

### 4.2. Один непрерывный конвейер на весь эфир

```
flvmux streamable=true name=mux ! rtmpsink location="rtmp://127.0.0.1:1935/live/stream"

concat name=vconcat ! queue ! <энкодер> ! h264parse config-interval=-1
    ! queue ! mux.
concat name=aconcat ! audiorate ! queue ! avenc_aac bitrate=<bps>
    ! aacparse ! queue ! mux.

# для каждого сегмента:
#   Image:
filesrc ! decodebin ! imagefreeze num-buffers=N ! video/x-raw,framerate=<fps>/1
    ! videoconvert ! videoscale ! <caps> ! queue ! vconcat.
audiotestsrc wave=silence samplesperbuffer=<rate> num-buffers=<sec>
    ! audioconvert ! audio/x-raw,rate=<rate>,channels=2,format=F32LE ! queue ! aconcat.
#   File:
filesrc ! qtdemux name=demuxN
    demuxN.video_0 ! queue ! decodebin ! videoconvert ! videoscale ! videorate
        ! <caps> ! queue ! vconcat.
    demuxN.audio_0 ! queue ! decodebin ! audioconvert ! audioresample
        ! audio/x-raw,... ! queue ! aconcat.
#   File без звука: вместо audio-ветки — audiotestsrc с тишиной той же длины.
```

**Почему один процесс:** `concat` держит одно соединение с MediaMTX от первого кадра
заставки до последнего кадра финала. Зритель не видит разрывов.

### 4.3. MediaMTX — ретранслятор и отправка на CDN

Генерируемый `mediamtx.yml`:

```yaml
logLevel: info
rtmp: yes
rtmpAddress: :1935
rtsp: yes
writeQueueSize: 2048
paths:
  live/stream:
    source: publisher
    forward:
      - dest: "rtmp://<host>/<app>#<streamKey>"
  all_others:
```

Без CDN (пустые URL/ключ) секция `forward` не пишется — локальный режим.

**Почему `forward`, а не отдельный `gst-launch` + `push.bat`:** нативная отправка MediaMTX
сама держит соединение и переподключается. Старая схема с `push.bat` зависала в
`PREROLLING` (видео не доходило до `flvmux`), из-за чего поток на CDN не поднимался вовсе.

**Почему ключ передаётся как `путь#ключ`:** MediaMTX разбирает адрес как URL и теряет
query-часть. При ключе вида `имя?auth=...` CDN получал запрос без токена и отвечал
`403 publish denied`. Форма `#` передаёт ключ целиком.

### 4.4. Превью — отдельный процесс

```
rtmpsrc location=rtmp://127.0.0.1:1935/live/stream ! flvdemux name=d
  d.video ! queue ! h264parse ! avdec_h264 ! videoconvert ! videoscale ! videorate
          ! video/x-raw,width=160,height=90,framerate=5/1 ! jpegenc quality=40
          ! tcpserversink host=127.0.0.1 port=<N> sync=false async=false
  d.audio ! queue ! fakesink sync=false async=false
```

C# подключается TCP-клиентом, читает поток и собирает кадры классом `JpegFramer`
(корректно переносит «хвост» кадра между чтениями).

**Почему отдельный процесс:** раньше превью было ветвью `tee` в эфирном конвейере, и любая
его ошибка останавливала весь пайплайн. Теперь падение превью не влияет на трансляцию.

**Почему RTMP, а не RTSP:** у `rtspsrc` несколько дорожек, и неподключённая звуковая
вызывает ошибку `not-linked`, от которой превью умирало сразу после подключения.

### 4.5. Окружение GStreamer и проверка энкодера

**Явное окружение.** Каждому дочернему процессу GStreamer задаются переменные:

```
PATH           = <tools>\gstreamer\bin;%PATH%
GST_PLUGIN_PATH = <tools>\gstreamer\lib\gstreamer-1.0
```

Без этого программа полагается на то, что GStreamer сам найдёт плагины рядом
с собой. Обычно так и происходит, но на чужой машине это неявная договорённость.

**Проверка энкодера перед эфиром.** После сборки плейлиста, но **до** запуска
планировщика, программа делает короткий пробный запуск (видеотест 640×360,
5 кадров, ~0,8 с). Если выбранный аппаратный энкодер не справился — конвейер
не собирается или энкодер отсутствует, — программа:

- переключается на `x264enc` (CPU);
- пишет в лог `>>> Энкодер <имя> не запустился — переключение на x264enc (CPU)`;
- меняет подсказку под полем кодека на предупреждение.

Так «есть драйвер, но не работает» выявляется до эфира, а не в момент старта.
Проверка выполняется заранее, поэтому на время начала трансляции не влияет.

### 4.6. Защита от ошибок настройки

Эфир, который «идёт», но не доходит до зрителей, — худший вид сбоя: оператор
уверен, что всё работает. Поэтому до старта и во время эфира действуют проверки.

**Проверка адреса CDN и ключа (до старта).** Перед запуском:

- адрес должен начинаться с `rtmp://` или `rtmps://`;
- в адресе должен быть сервер (хост);
- не допускаются пробелы в адресе и ключе;
- ключ не должен содержать кавычек и переносов строк;
- если адрес заполнен, а ключ пуст (или наоборот) — это ошибка, эфир не стартует.

**Подтверждение локального режима.** Если адрес и ключ пустые, программа спрашивает:
«Эфир пойдёт ТОЛЬКО локально, зрители на CDN его не увидят. Продолжить?»
Молча уходить в локальный режим нельзя.

**Сигнал при отказе CDN.** Если MediaMTX получает отказ (`bad result`), программа:

- красит плашку CDN в красный с причиной (`публикация отклонена`, `403`, `401`, `таймаут`);
- пишет в строку состояния: `ВНИМАНИЕ: CDN отклонил поток — эфир идёт только локально`;
- сообщение выводится один раз на попытку, чтобы не мигало при переподключениях.

**Проверка порта.** До запуска MediaMTX проверяется, свободен ли порт 1935.
Если занят — сразу понятное сообщение («второй экземпляр или старый MediaMTX»),
а не «сервер не открыл порт за 10 секунд».

**Маскировка ключа в логах.** Все строки перед записью проверяются: ключ потока
заменяется на `***`. Логи пересылают при разборе проблем, а ключ — это доступ к эфиру.

**README.txt** входит в комплект: требования, запуск, поддерживаемые форматы,
настройка CDN, где логи, известные ограничения.

**Кнопка «Открыть логи»** (внизу слева) открывает папку логов в Проводнике
с выделением `stream_log.txt`. Рядом подпись с точным путём. Без неё на чужой
машине `%TEMP%` приходится искать вручную, а он бывает на другом диске.

**Один экземпляр и уборка «сирот».** В `Program.Main` берётся системный Mutex:
второй запуск показывает предупреждение и завершается. При старте форма
вызывает `KillStaleChildProcesses()` — завершает `mediamtx` и `gst-launch-1.0`,
запущенные **из папки этой программы** (путь проверяется, чужие процессы
с такими же именами не трогаются). Это нужно после аварийного закрытия:
иначе процессы держат порты 1935/8554 и мешают удалить папку. Тот же сбор
процессов выполняется и в `StopMediaMtx()` при выходе.

### 4.7. Тестовый цикл (второй режим)

Помимо эфира по расписанию программа умеет держать **непрерывный тестовый поток**:
для проверки канала, ссылок, встраивания плеера, приёмки выездной площадки.

Переключатель режима — в блоке «Настройки трансляции». Меняются только
несколько полей; кодирование, CDN, профили и превью работают одинаково.

| Поле | Эфир по расписанию | Тестовый цикл |
|---|---|---|
| Время старта | дата и время | — (старт сразу) |
| Длительность | — | минуты, `0` = до остановки |
| Источник | Main Video | файл / картинка + тон / тестовая таблица |
| Часы на экране | — | галочка (`clockoverlay`) |

**Источники цикла:**

- **файл** — повтор выбранного ролика; число повторов = длительность / длина ролика,
  но не больше 60 веток в конвейере (защита от неподъёмной командной строки);
- **картинка + тон 1 кГц** — одна ветка `imagefreeze` на всю длительность
  и `audiotestsrc wave=sine` вместо тишины;
- **картинка + MP3** — картинка из поля «Источник» и внешний звуковой файл
  (`mp3/m4a/aac/wav`). Файл выбирается сразу при выборе пункта списка и
  запоминается в профиле (ключ `LoopAudio`). Плейлист режется на сегменты
  длиной в один проигрыш звука: каждый сегмент — картинка нужной длины плюс
  один проигрыш MP3;
- **тестовая таблица** — `videotestsrc pattern=smpte` + `audiotestsrc wave=ticks`
  (щелчок раз в секунду), файлы не нужны.

**Точная длина звука в сегменте.** MP3 редко бывает целое число секунд, а `concat`
требует одинаковой длины видео и звука в каждом сегменте — иначе рассинхрон
накапливается с каждым повтором. Поэтому звук режется по кадрам:

```
filesrc ! decodebin ! audioconvert ! audioresample ! audio/x-raw,...
  ! audiobuffersplit output-buffer-duration=1/<fps>
  ! identity eos-after=<кадры>
```

Проверено: MP3 длиной 20 с при картинке 10 с даёт на выходе ровно 9,98 с —
лишнее отбрасывается, сегменты стыкуются точно.

**Часы на экране** — `clockoverlay` после склейки, перед энкодером: время видно
на всех сегментах. Сравнение с настенными часами даёт задержку CDN.

**Почему часы отставали (исправлено).** Очереди перед `flvmux` были без
ограничений (`max-size-* = 0`), поэтому кодировщик уходил вперёд на минуты:
поток всё равно шёл в реальном времени (его придерживает `rtmpsink` с `sync`),
но `clockoverlay` рисовал время **кодирования**, а не отправки. На экране это
выглядело как «секунда идёт за шесть» — и отставание росло с длительностью эфира.
Ограничение очередей двумя секундами создаёт обратное давление: кодировщик
идёт вровень с отправкой. Проверено: кадры, отстоящие на 8 секунд эфира,
показывают ровно 8 секунд разницы.

**Остановка по времени.** Момент окончания запоминается при старте; таймер
останавливает процесс, и эфир помечается как **«Тест завершён по расписанию»**,
а не «прерван» — плановая остановка не должна выглядеть аварией.

**Заставок в цикле нет.** Intro и outro добавлялись и раньше, из-за чего
плейлист становился длиннее заказанного времени (60 + 300 + 60 = 7 минут
на «5 минут теста»), а таймер обрывал эфир на 5-й минуте — финал не доигрывал.
Теперь в режиме цикла эти сегменты не создаются, поля Intro/Outro в интерфейсе
неактивны, и длительность потока равна заказанной. Момент остановки берётся
с запасом 15 секунд, чтобы штатный конец плейлиста успевал сработать раньше
таймера (код 0 вместо принудительного завершения).

### 4.8. Планировщик

- `DateTimePicker` с точностью до секунды, по умолчанию `now + 2 мин`.
- Таймер 1 с: по достижении времени — `StartPreparedStream()`.
- Подготовка плейлиста занимает **доли секунды** (нет предварительного кодирования),

## 5. Параметры кодирования

| Параметр | По умолчанию | Примечание |
|---|---|---|
| Разрешение | 1920x1080 | парсится как `ШxВ` |
| FPS | 25 | |
| Видео | 4200 kbps | |
| Аудио | 192 kbps | в конвейер уходит ×1000 (bps) |
| Частота звука | 48000 Гц | |
| Энкодер | Авто (лучший доступный) | детект через `gst-inspect-1.0` |

Строки энкодеров (ключевой кадр — **раз в секунду**, `gop = fps`):

| Энкодер | Строка |
|---|---|
| nvh264enc | `nvh264enc bitrate=<kbps> gop-size=<fps> rc-mode=cbr zerolatency=true` |
| x264enc | `x264enc bitrate=<kbps> key-int-max=<fps> speed-preset=veryfast tune=zerolatency` |
| qsvh264enc | `qsvh264enc bitrate=<kbps> low-latency=true` |
| amfh264enc | `amfh264enc bitrate=<kbps×1000> usage=low-latency` |
| msdkh264enc | `msdkh264enc bitrate=<kbps> rate-control=cbr` |

**Почему ключевой кадр раз в секунду:** плеер и упаковщик CDN подключаются только к
ключевому кадру. При редких ключевых кадрах (по умолчанию ~10 с) зритель «прыгает» в
середину, а CDN дольше стабилизируется. Так же делает vMix (`-g:v 25`).

**Почему `rtmpsink` без `sync=false`:** `sync=false` отключает привязку к системным часам,
и конвейер отдаёт кадры с максимальной скоростью — 5-минутный плейлист «пролетает» за
20 секунд, MediaMTX захлёбывается (`reader is too slow`), CDN рвётся.

## 6. Заставки (intro / outro)

- Источник — выбранная пользователем картинка (JPG/PNG) либо встроенный ресурс.
- Длительность intro задаётся в секундах: **минимум 40, по умолчанию 60**.
- Длительность outro — 60 секунд (фиксирована).
- Картинка декодируется **один раз** и повторяется кадр за кадром (`imagefreeze`).

**Откуда 60 секунд (обоснование из практики).**
Провайдер раздаёт HLS с сегментами по 10 секунд. Плееру нужно **2–3 сегмента**,
чтобы набрать буфер и стабилизироваться: это 20–30 секунд, а на боевом сайте
с круглосуточным эфиром наблюдалось ~40 секунд до устойчивой картинки.
Плюс время на приём потока самим CDN. Заставка в 60 секунд покрывает это
с двукратным запасом; 120 секунд — избыточно и удлиняет эфир без пользы.

С этим напрямую связан интервал ключевых кадров: HLS-сегмент режется **только
по ключевому кадру**. При ключевых кадрах раз в 10 секунд CDN не мог собрать ровный
10-секундный сегмент и ждал ближайший кадр, растягивая старт плеера. При `gop = fps`
(кадр раз в секунду) сетка ровная, и сегменты собираются без задержек.

**Почему не заранее закодированные MP4-«кирпичики»:** старая схема кодировала 5-секундный
ролик и повторяла его N раз. Это давало: задержку подготовки (минута статики — 52 секунды
кодирования при CPU-энкодере), кратность длительности 5 секундам, 12 отдельных веток в
конвейере (на часе заставки — 720) и временные файлы в `%TEMP%`.

## 7. Работа с файлами

- Поддерживаются контейнеры **MP4 / MOV / M4V**. Для прочих выводится понятное сообщение
  с предложением пересохранить файл.
- Файл **без звуковой дорожки** не ломает эфир: подставляется тишина той же длины,
  синхронизация не съезжает.
- Анализ файла (`gst-discoverer`) даёт длительность, разрешение, fps, кодеки, битрейт.
  Битрейт понимается в обоих форматах (`4000 kbps` и `5564746` — биты/с), берётся
  **только видео-битрейт** (строка аудио не перезаписывает его).
- Результат анализа показывается под полем с цветовой индикацией:
  зелёный — всё совпадает, оливковый — отличается разрешение, тёмно-красный — кодек/битрейт.

## 8. Профили (INI)

`GstScheduler.cfg`:

```ini
[Default]
Resolution=1920x1080
Fps=25
VideoKbps=4200
AudioKbps=192
SampleRate=48000
RtmpUrl=rtmp://
StreamKey=
```

- Сохранение — кнопкой и автоматически при переключении профиля.
- Удалить последний профиль нельзя.
- Пустое имя профиля не допускается.

**Почему INI:** без сторонних библиотек, 100% совместимо с AOT, читается человеком.

## 9. Логирование

Все три файла лежат в `%TEMP%\GstScheduler\prep\`.

**Ротация.** Перед новым прогоном существующий лог не удаляется, а переименовывается
по времени последней записи: `stream_log_3F7A21C4_2026-11-04_11-25-51.txt`. Хранятся
последние **20** копий каждого лога, более старые удаляются.

**Идентификатор машины и вид сборки — в имени каждого файла.** Активные логи
называются `stream_log_<ID>.txt` (обычная версия) и `stream_log_srt_<ID>.txt`
(SRT-версия); архивы получают ту же основу плюс отметку времени. Раньше метка
вида сборки добавлялась только при архивации и показывала сборку, которая файл
*архивировала*, а не ту, что в нём записан, а активные файлы с разных машин
назывались одинаково и перезаписывали друг друга при сборе в одну папку.
Теперь имя уникально всегда.

**Итоговая строка пишется всегда.** Помимо штатного конца плейлиста и остановки
по расписанию, `=== Эфир завершён … ===` дописывается при аварийном стопе
(`остановлен оператором`) и при закрытии окна во время эфира (`программа закрыта`).
Иначе такие прогоны оставались бы в истории без конца.

**Идентификатор машины.** Восемь символов, вычисляются один раз из имени компьютера,
пользователя и версии ОС (SHA-256) и сохраняются в `machine.id` рядом с настройками.
Нужны в имени лога, чтобы при сборе логов с нескольких машин файлы не перезаписывали
друг друга.

| Файл | Содержимое |
|---|---|
| `stream_log.txt` | шапка (окружение, энкодер, параметры, плейлист, полная команда) + вывод `gst-launch` + отметка декодера |
| `mediamtx_log.txt` | вывод MediaMTX, включая ответы CDN |
| `preview_log.txt` | вывод процесса превью |

Шапка `stream_log.txt` содержит **окружение машины**, чтобы прогоны с разных компьютеров
можно было сравнивать:

```
=== Эфир начат: 03.11.2026 01:45:12 ===
Компьютер: ИМЯ-ПК (пользователь)
ОС: Microsoft Windows 10.0.19045
CPU: Intel(R) Xeon(R) CPU E5-2686 v4 @ 2.30GHz [64 потоков]
ОЗУ: 127.9 ГБ
GPU: NVIDIA GeForce GTX 1080; NVIDIA GeForce RTX 2080 Ti
Энкодер: nvh264enc (аппаратный, NVIDIA NVENC)
```

Данные берутся без сторонних библиотек: процессор — из реестра
(`HARDWARE\DESCRIPTION\System\CentralProcessor`), память — `GC.GetGCMemoryInfo()`,
видеоадаптеры — перебор драйверов класса `{4d36e968-...}`.

**Декодер определяется по факту**, а не по настройке: GStreamer пишет
`Got context from element 'd3d12h264dec0'` — из этой строки берётся имя элемента
и в лог добавляется `>>> ДЕКОДЕР: d3d12h264dec0 (аппаратный)`. Если за весь эфир
аппаратный декодер не проявился, в конце пишется
`>>> ДЕКОДЕР: программный (аппаратный не использовался)`.

**Почему шапка обязательна:** без неё невозможно понять, какой файл, на какой машине
и с какими параметрами играл эфир, когда что-то идёт не так.

## 10. Индикация в интерфейсе

Строка состояния (`SetStatus`) — фазы эфира:

| Статус | Цвет |
|---|---|
| Idle «Готов» | Gainsboro / DimGray |
| Waiting «Ожидание старта» | LightSteelBlue / MidnightBlue |
| Intro «Заставка (intro)» | LightSkyBlue / DarkBlue |
| Main «Основной файл: имя» / «Тестовая таблица» / «Цикл: картинка» | MediumSeaGreen / White |
| Outro «Финальная заставка (outro)» | SandyBrown / DarkRed |
| Ok «Эфир завершен» / «Тест завершён по расписанию» | PaleGreen / DarkGreen |
| Error «Эфир прерван (код N)» | Crimson / White |

**Фазы вычисляются по плейлисту.** Раз в секунду таймер сравнивает прошедшее время
с суммой длительностей сегментов и показывает, что играет сейчас. Текст меняется
только при переходе на новый сегмент — без мигания.

Отдельная плашка **CDN** (читается из ответов MediaMTX в реальном времени):

| Надпись | Значение |
|---|---|
| `CDN: не настроен` | URL/ключ не заполнены, локальный режим |
| `CDN: ожидание` | эфир ещё не запущен |
| `CDN: подключение...` | начата публикация |
| `CDN: публикация идёт` | 8 секунд без отказа — поток принят |
| `CDN: ПУБЛИКАЦИЯ ОТКЛОНЕНА` / `ОТКАЗ 403` / `ОТКАЗ 401 (ключ)` / `ТАЙМАУТ` | отказ CDN |
| `CDN: нет подтверждения` | 20 секунд без ответа — смотреть лог |
| `CDN: остановлен` | эфир завершён или аварийно остановлен |

**Почему отдельная плашка:** пользователь должен видеть реакцию провайдера, не открывая лог,
и при этом не путать её с фазой эфира.

## 11. Аварийный стоп и завершение

`btnEmergencyStop`:
1. отмена подготовки (если идёт);
2. остановка таймеров;
3. `Kill(entireProcessTree: true)` для эфирного процесса, MediaMTX и превью;
4. сброс прогресса и статусов.

`Form1_FormClosing`: то же + автосохранение активного профиля.

## 12. Проверено на практике

| Проверка | Результат |
|---|---|
| Реальное время | ролик 20 с проходит за 20,5 с |
| Длинный эфир | 18 минут без рассинхрона и разрывов |
| Ключевые кадры | замер по кадрам: 0, 1, 2, 3 с — ровно 1 кадр/с |
| CDN | поток принят, `forwarding to ...`, без отказов |
| Превью | 21 кадр за 4 секунды при 5 к/с |
| Файл без звука | конвейер собирается, эфир идёт |
| Отмена подготовки | без ложного окна ошибки |

## 13. Известные ограничения

1. **Только MP4/MOV/M4V.** MKV/AVI не читаются — выводится сообщение.
2. **Микро-скачок меток звука на стыке сегментов** (~0,3–5 мс, следствие дополнения
   последнего AAC-кадра). Проверено: присутствует и на файлах, которые CDN принимает
   идеально, поэтому не является дефектом.
3. **Тяжёлые файлы** (например, 35 Мбит/с + PCM 24 бита) могут давать сбои на стороне CDN
   в первые секунды. Рекомендация: нормализовать файл (видео копией, звук в AAC).
4. **Outro фиксирован 60 секундами**, отдельного поля нет.
5. **Процессы из `push.bat` больше не отслеживаются** — батник удалён вместе со схемой.

## 14. История решений

| Было | Стало | Почему |
|---|---|---|
| MP4-«кирпичики» 5 с × N | `imagefreeze` прямо в эфире | нулевая подготовка, точная длительность, 1 ветка вместо 12 |
| Превью — ветка `tee` в эфирном пайплайне | отдельный процесс | ошибка превью роняла весь эфир |
| Превью по RTSP | превью по RTMP с обеими дорожками | `rtspsrc` падал с `not-linked` |
| `push.bat` + второй `gst-launch` | нативный `forward` MediaMTX | старый конвейер зависал в `PREROLLING` |
| Ключ как хвост URL | `путь#ключ` | CDN терял `?auth=` и отвечал 403 |
| `rtmpsink sync=false` | синхронизация с часами | поток «пролетал» в 15 раз быстрее |
| Ключевой кадр ~10 с | раз в секунду | медленное подключение зрителей и CDN |
| Битрейт парсился как kbps | оба формата, только видео | ложные предупреждения о файле |
